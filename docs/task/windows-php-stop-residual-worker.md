# Windows PHP 停止后额外 worker 的回收

## 现场与源码结论

用户并行退出日志中，PHP 7.3 的 spawner PID=440 的普通权限树停止完成，随后模块报 `PHP processes are still running; PIDs=19860`，用户确认仍有一个 php-cgi 存活。其他 PHP 版本及 nginx/mysql/mailpit/redis 各自完成；main 将 PHP 7.3 记为 failed，而非提前注销。

这里有两个不同确认范围：公共 `ServiceStop.stopWindowsServiceProcesses` 在执行根停止后，确认首次列表选中的 PID/创建身份已消失；PHP 随后使用同一末次完整列表检查本版本 EXE 与 FlyEnv 专用 ini 的进程。后者能发现不在首次集合中的额外 worker。此前发现后直接抛错，没有尝试回收已明确归属本实例的剩余进程。

首次全量列表与执行之间存在权限管道准备和系统调度等待，首次快照不保证包含之后生成的 worker。现有日志没有打印 19860 的前后创建时间与初始完整目标，因此不能断言其具体生成时点或 taskkill 的内部顺序；本次修复确定存在的“检测到本版本额外 worker 后直接报错”缺口，并补充快照诊断证据。

## 操作契约

- 所有者仍是 `src/fork/module/Php.win/index.ts`，请求仍经过既有 InstalledItem、main 登记队列/退出并行编排及 fork `stopService`。
- 额外目标仅由 PHP 模块根据实际安装 EXE、专用 ini、可读创建身份筛选；公共执行器负责树根压缩、身份复核、权限分流和退出确认。
- 状态只存在于本轮 fork 请求内，不新增 renderer 状态、Pinia、配置或 IPC；停止总流程仍属于已有请求预算。
- 普通树停止成功且模块残留列表非空时，最多执行一次补停；正常成功路径不增加系统查询或执行动作。
- 补停成功后再次检查本版本残留，全部完成才清理 PID 文件并发送成功终态；补停失败或再次残留均保留失败语义。
- 不改变启动组串行规则，不改变退出多实例并行编排。不同 PHP 实例仅回收各自安装/ini 匹配的目标。
- 未新增或运行测试、构建或真实服务操作，本轮仅进行源码复核和语法/差异检查。

## 修改内容与完整停止顺序

本次修改只涉及 PHP Windows 模块及文档：

1. 从停止前完整列表识别本版本 spawner 根；已确认的父授权其完整后代。父已缺席的独立 worker 仍必须通过实际安装路径和专用 ini 确认归属。
2. 原首次目标集合交给公共 `stopWindowsServiceProcesses`；执行端继续从首次列表取得根创建身份并在实际派发前复核，不为普通 worker 单独采样。
3. 公共退出确认返回新鲜完整列表；PHP 使用现有 `fastCgiProcesses` 在内存筛选本版本残留，无额外查询。
4. 如果有残留，记录 `[PHP][stop][recover-residuals]`：版本、首次目标、残留 PID/PPID/创建时间、相同 PID 首次创建时间、是否曾被选为初始目标。日志不输出完整命令行。
5. 使用该末次列表作为补停的首次身份快照。已独立确认的残留根连同其当前完整后代交给**同一个公共执行器**，不新增直接 kill 分支，不用旧父的历史 PPID 授权，不拿第一次列表的旧身份授权新 worker。
6. 补停的退出确认返回最终列表。成功停止的额外 PID 合并入 `APP-Service-Stop-PID` 的结果集合；再次进行本版本残留检查。
7. 若仍有残留，继续报错；否则用最终列表清理本次候选对应的私有 PID 文件，并返回真正成功终态。main 按原冻结 generation 注销。

## 边界与为何只补停一次

- 原首次目标仍存在时，公共退出等待会直接失败；本次未把该错误吞掉或改为无限重试。
- 只有末次列表中可明确证明归属的额外根进入补停。字段不可读/归属不匹配的候选沿用现有过滤规则，不能授权仅同名或同 EXE 的其他实例。
- 根自然退出或 PID 身份变化仍由公共执行器处理；命令失败、权限拒绝、UAC 取消、查询错误及退出超时继续向上传播，PID 文件不会提前清除。
- 正常情况下首次 spawner 已结束，额外 worker 不再由它补充；一次异常回收足以覆盖这类遗漏。如果外部程序持续按相同命令重启，有限补停后继续报告残留，防止退出无限等待。
- 正常路径仍是停止前和停止后的两次完整查询；异常补停仅复用已返回列表开始执行，再由公共执行器做必要的停止后查询。存在持续原树等待时沿用原轮询规则。
- Helper、UAC、管理员模式均从 PHP fork 到相同共享执行器，再走既有权限路由，因此补停对这些方式都有效；本次不修改 Go RPC 或 Go 执行器代码，不提升 Helper 版本。
- 并行退出的其他实例不因本实例异常提前中断；本实例全部确认完成之前仍保持未成功状态。

## 复核与实机观察

本轮源码复核涵盖 PHP 归属筛选、共享退出确认/身份快照、公共树根压缩与权限路由。后续实机退出若进入异常分支，会额外出现 `[PHP][stop][recover-residuals]`；耗时观察开启时可见 `php.stop.recover-residuals` 阶段。正常无残留时不出现该阶段。

后续诊断增强已将原补停日志并入带 stopId 的 `[ServiceStop][diagnostic]`，对应 stage 为 `php.recover-residuals`，并补齐首次目标、实际执行端和末次列表。最新字段与根因判断依据见 [Windows 服务停止诊断日志](windows-service-stop-diagnostics.md)；本节上述 Go 未修改/未升级说明仅对应有界补停那一轮，诊断轮已同步 Go 日志并升级为 33。
