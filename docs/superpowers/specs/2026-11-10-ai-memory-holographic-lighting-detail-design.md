## 2. 问题与依据

### P1 输出链没有统一的最终颜色转换

**已确认的代码事实：** `scene.ts` 的后处理链目前只有 `RenderPass → UnrealBloomPass`。虽然 renderer 设置了 sRGB 输出、ACES tone mapping 和曝光，但没有独立 `OutputPass` 统一处理组合后的画面。

本地安装的 Three.js 中，`UnrealBloomPass` 作为最后一个 pass 时，先用内部 `MeshBasicMaterial` 把底图绘制到屏幕，再用基于 `CopyShader` 的材质叠加 Bloom。底图与 Bloom 因此没有共同经过一次最终输出转换。`OutputPass` 则提供组合后的 tone mapping 和颜色空间转换。

**仍需对照验证的影响：** 这可能影响底图、辉光和高光之间的比例与颜色。不能仅凭缺少 `OutputPass`，就将所有偏白、偏暗或背景边界归因于这一项。应先固定模型与全部美术参数，单独校正输出链并对比，再决定后续调参。

### P2 主环偏白、偏硬，弧段端部齐整

**画面表现：** 主轨已经从细线变为有宽度的带状结构，但部分主环呈现近白色的连续亮芯，轮廓接近硬质细管，断点也比较整齐。

**代码依据：** 核心主轨默认使用 `IVORY`；同一弧段大部分顶点共享固定颜色和 energy。`ribbon-material.ts` 主要按横向 `vSide` 生成亮芯与柔边，缺少沿路径的局部明暗和端部淡出。`ribbon.ts` 在路径未提供 alphas 时默认使用 1。

**优化重点：** 保留宽度，将长距离均匀高光改为暖金底光、局部暖白高光和有组织的断续细节。

### P3 中外层仍显稀疏，细节组织不够强

**画面表现：** 中心网络较密，外层仍由少量大弧和散落折线主导，中外层存在较大空区。

**代码依据：** 当前已经有 96 组沿主轨附着的细节、32 组径向连接和 24 组纤维支路，不能再判断为“没有中层结构”。但部分附着细节只是对主轨采样点做小幅径向偏移，容易与主轨重叠；其他碎片则仍按球面或半径分布，未形成足够可读的局部电路束。

**优化重点：** 先让已有细节在轮廓、尺度和方向上可辨，再少量补足结构空区。

### P4 安全视口露出矩形背景边界

**画面表现：** canvas 已收进 HUD 之间，矩形区域比周围页面更黑，边界可以被看出。

**代码依据：** `#neural-scene` 使用独立矩形布局，`scene.background` 是不透明颜色；页面则有自己的底色和径向渐变。WebGL 输出还经过后处理和 tone mapping。两处填写相同的十六进制颜色也不保证最后显示相同。

**优化重点：** 保留安全视口及其拾取坐标，统一整个页面的背景合成规则。

### P5 分类视图中仍有非必要的环与光晕

**画面表现：** 当前分类和直接邻居已经更清楚，但其他分类的中枢环、部分装饰和光晕仍会占据较大画面面积。

**代码依据：** 普通边已改用 `edge-material.ts`，节点也已有焦点权重。中枢 Sprite 虽然淡化，`createHubRing()` 生成的环仍使用单独固定材质；静态装饰和关系边没有完全一致的聚焦表达。

**优化重点：** 区分有意义的直接邻居与纯装饰。直接邻居继续保留，无关中枢及其环进一步退后，不能通过隐藏全部其他分类来破坏跨分类关系。

## 3. 处理路径

只继续提高曝光或 Bloom，无法同时改善主环质感和细节组织，且可能先造成高光失色。改用复杂体积渲染或新引擎则会增加不必要的实现与维护成本。

推荐在现有实现上依次完成：**统一输出 → 统一背景 → 主环光感 → 结构细节 → 分类视图收敛**。输出和背景先稳定，后续材质调整才有可靠的比较基础。

## 4. 统一输出链并建立可比较的基线

### 4.1 改为组合后统一输出

推荐链路为 `RenderPass → UnrealBloomPass → OutputPass`。由 EffectComposer 决定最后一个启用 pass 的 `renderToScreen`，不要额外在某个场景材质或 Bloom 上强制直出屏幕。

场景和 Bloom 在中间渲染目标内使用线性工作空间；最终 `OutputPass` 读取 renderer 的 ACES tone mapping、曝光及 sRGB 输出设置，统一处理组合结果。暂时保持现有曝光 1.12 和 Bloom 的 strength、radius、threshold 不变。

现有 Shader 中的 Three.js tone mapping 与 colorspace include 不应被机械删除。先核对本地版本在离屏目标中生成的 Shader 变体，确保中间阶段没有手写 gamma、sRGB 编码或重复 tone mapping。所有通过十六进制指定的颜色统一经过 `THREE.Color` 转换；直接写在 Shader 中的颜色 uniform 明确使用线性值。

新增 `OutputPass` 由 `NeuralScene` 持有并在 dispose 时释放。resize 沿用现有 composer 路径，不创建第二套渲染循环或 renderer。

### 4.2 三组对照，分别回答不同问题

固定模型种子、相机、根旋转、动画时间、尺寸和 DPR，保存以下结果：

1. 现有输出链，保留作为本轮原始基线。
2. 加入 `OutputPass`，其他参数完全相同，用于判断统一输出带来的实际变化。
3. 正确输出链下关闭 Bloom，用于区分底光与辉光各自的贡献。

另做一次诊断对照：`RenderPass → OutputPass` 与 `RenderPass → strength 为 0 的 Bloom → OutputPass` 应在容许的数值误差内一致。用已知线性灰阶和暖金色块检查输出变换及高光变化；诊断图仅用于验收产物，不放进正常用户界面。

如果第二组整体观感改变，记录原因和参数，再开始美术调整。不能为了恢复旧截图而立即拉回曝光，也不能只凭“更亮了”宣称输出修复正确。

## 5. 背景融合采用同一黑底和全屏氛围层

### 5.1 推荐方案

保留现有安全视口矩形。将页面基础背景和 WebGL 基础背景统一为纯黑：页面根、body 和观测容器的基底使用 `#000000`，`scene.background` 也使用黑色不透明背景。零 RGB 在统一输出链中仍为零，避免深蓝底色分别经过 CSS 与 tone mapping 后产生差异。

深黑蓝氛围通过 canvas 上方、HUD 下方的同一个全屏 CSS 层提供。该层覆盖整个观测区域而非仅覆盖 canvas，使用很弱的蓝色径向渐变、现有网格或暗角，并保持 `pointer-events: none`。删除或迁移原先只位于 canvas 后方的径向渐变，避免再次被不透明 canvas 挡住。

黑底与全屏氛围层按同一规则跨越 canvas 边界，HUD 面板继续保留自己的半透明深蓝底。氛围层应足够弱，不能像半透明面板一样显著压住主体对比度。

### 5.2 本轮不采用的方式

不建议只把 `scene.background` 设为 null 就结束：renderer 的 alpha 选项不等于整个 Bloom 链都能正确保留透明背景，可能出现 alpha 被覆盖、黑边或不一致的预乘叠加。

也不建议重新把 canvas 铺满屏幕来掩盖矩形边界；那会使已稳定的安全视口和拾取规则重新变复杂。本轮不新增透明 Bloom 或独立背景合成 pass。

### 5.3 验收

分别在全局、分类和单点模式检查 canvas 的四条边。背景上不应出现颜色突变、矩形暗块或渐变被截断；布局尺寸改变后仍保持一致。主体轮廓、标签和 HUD 操作不能因此被裁切或遮挡。

## 6. 主环保留厚度，改变沿途光感

### 6.1 增加沿弧段与父路径的坐标

在现有 `RibbonPath` / 几何属性中增加弧段局部进度和父环路径进度，分别用于端部渐隐与连续的结构纹理。进度按累计长度计算，不能按屏幕位置生成随机噪声，也不能让旋转导致纹理在表面滑动。

静态轨道和动态尾迹共用几何工具，但通过明确的材质用途或参数区分。动态尾迹已具有头尾 alpha 包络，不能直接套用静态弧段双端渐隐，使流光头部消失。静态轨道的调色与纹理也不能无意改变语义脉冲。

### 6.2 三层光感

- **稳定底光：** 主体使用琥珀金，建议先从 `#e8a933` 一类暖金起调。保留完整可读的轨迹，避免整段都是近白色。
- **局部亮芯：** 高光可向 `#ffe0a3` 过渡，暖白集中在少量能量峰值与交汇处。颜色以线性 uniform 传入，并控制能量，避免加法叠加后长距离失色。
- **柔光边缘：** 沿用现有屏幕空间带宽，调整亮芯占比和外沿衰减。先保持当前 4.5–5 CSS px 的整体宽度，减少硬亮芯占比，不继续整体加粗。

高光能量先通过 Shader 的平滑包络控制，再用 Bloom 提供少量外溢。对比时应能分清稳定底光和移动能量，不能整条主轨同时达到近白高光。

### 6.3 端部与断续纹理

弧段前后约 5%–10% 长度先采用平滑 alpha 渐隐，使断点自然消退。过短弧段限制渐隐长度，保留中部可辨结构。避免所有弧段同一时刻一起淡出。

沿父路径加入确定性的短亮片、弱缺口和局部能量起伏，纹理在同一个环上连续，只有能量包络缓慢变化。微缺口应保留底光，不把主环切成许多孤立亮棒；原有较大几何缺口继续由现有 coverage 控制流光淡出。

纹理与端部 alpha 相乘后，再结合深度与聚焦权重。横向柔边与纵向渐隐分别控制，避免端部仍出现一条齐整的横切亮边。带状几何仍需保留退化切线保护，检查环架侧对镜头、重复采样点及路径首尾时没有尖刺或 NaN。

## 7. 重新组织现有中外层细节

### 7.1 先重分配，后增加

先把现有 `attachment: orbit / radial / fiber` 三类细节分开观察，在相同镜头下确认它们是否实际可见。第一轮不增加总数，优先调整现有 96 组轨道附着细节、32 组径向连接和 24 组纤维支路。

尤其需要避免轨道细节在投影后与主轨重合。沿轨道局部切线、径向与侧向构建坐标框架，生成小尺度平行段、横档和阶梯电路；侧向偏移与径向错层共同使用，不能只把原曲线径向缩放后复制一遍。

### 7.2 按结构分配可见细节

- 核心主环附近形成少量密集的短电路束，建立精密感。
- 中层纤维附近保留稀疏支路，让中心网络延伸到主体中部。
- 外壳局部形成有横档和刻度的短轨道束，在部分区域建立清晰轮廓，其余区域保持空隙。

细节附着在同一运动组，使用该组局部坐标；不要跨独立旋转组拉一条固定连接。现有模型的确定性随机种子、语义节点和关系端点保持不变。新增装饰不进入 Raycaster，也不计入业务计数。

完成上述重分配后，若相同尺寸的远景仍显空，允许补充少量短结构。首次新增装饰顶点控制在本轮基线的 25% 以内，优先使用既有材质和分组批次；这个上限是成本约束，不是必须填满的目标。

### 7.3 保证远景也能读出细节

在实际默认镜头下判断细节是否可辨，不能只看放大图。远层主要通过局部结构束的整体明暗被读到，近层再显示内部细线；必要时对相邻细节的能量做轻微分组，而非把每条线都加粗。

保留核心到中层再到外层的密度变化，避免整球均匀铺满。新增几何重新参与装饰主体边界计算，确保呼吸、旋转和缩放时仍遵守现有安全视口。

## 8. 分类聚焦只保留有意义的外围信息

保留当前相机目标集合：本类全部节点、中枢和跨分类直接 semantic 对端。不要因视觉降噪而删去这些对端，或把已完成的关系权重改回全网统一亮度。

把 `createHubRing()` 生成的材质和所属分类登记在 `NeuralScene`，同其他图层使用同一聚焦状态：全局保留原有弱提示；分类模式中当前中枢环保持克制，对端记忆不自动带亮其分类中枢环，无关中枢环隐藏或降至接近不可见。

无关中枢 Sprite 和装饰轨道可比直接邻居更暗。直接邻居保留节点和对应 semantic 边即可，不展开对端分类的 membership 网络。选中单条记忆时仍只高亮直接 semantic 关系；visual 和新增装饰不进入关联数量。

所有焦点变化通过现有 `NeuralScene` 命令更新，重置后恢复全部材质与标签状态。分类淡化不应修改 DOM 计数、关系模型或节点的可归属信息。

## 9. 文件分工、生命周期与失败边界

- `scene.ts`：加入并释放 OutputPass；统一基础背景；登记中枢环聚焦状态。保留已完成的相机拟合和普通关系边 Shader。
- `style.css`：页面纯黑基底和统一全屏氛围层；保留安全视口与 HUD 操作布局。
- `ribbon.ts`：增加长度进度、端部和纹理所需批量属性；保持现有路径度量及动态尾迹兼容。
- `ribbon-material.ts`：静态主轨用途参数、横向光感、纵向包络与暖金颜色控制。
- `entity-model.ts`：主轨元数据和装饰附着细节重分配，更新保守边界；业务模型不变。
- `entity-scene.ts`：绑定新增属性与 uniform，协调已有 flow coverage、深度、减少动态和聚焦，释放新增 GPU 资源。
- 现有 `capture.ts` 与相关测试：固定画面状态生成输出链对照、端部近景、全局及聚焦证据；诊断不进入正常 HUD。

这些状态都不超过当前预览页面的生命周期。相机和渲染资源由 `NeuralScene` / `NeuralEntity` 持有；页面隐藏暂停，销毁释放，快速切换复用现有“最新目标替换旧目标”机制。不新增 Pinia、持久化、跨页面 singleton controller、IPC 或外部进程，没有模块边界例外授权。

输出链校正是后续光感标定的必要依赖，未确认前不要同时调整曝光和材质。背景、细节及分类收敛可分别记录结果；单项视觉不达标不否定已确认的其他项。Shader 编译、拾取或资源释放失败必须修复，不能以视觉降级掩盖。截图保存等附加动作失败只报告该动作，不重建场景或重放用户选择。

## 10. 实施顺序与验收

### 阶段 A 输出与背景

完成统一输出及三组画面对照，再统一黑底和全屏氛围层。确认无重复颜色转换，零 Bloom 诊断对照一致，画布边界消失。该阶段不得同时改变模型、主轨颜色、宽度或数量。

### 阶段 B 主轨光感

在阶段 A 参数冻结后调整暖金底光、局部高光、端部渐隐与断续纹理。交付同尺寸全局截图、端部近景和不少于 10 秒的旋转片段。验收重点是环架可读、端部自然、局部高光明确，长距离近白硬管感减弱。

### 阶段 C 细节与分类

先重分配已有细节，分别查看正面、侧面和至少两个中间角度，再决定是否增加数量。随后收敛中枢环和无关光晕，交付全局、项目分类及单节点关系截图。

八个分类均检查一次聚焦、直接跨分类关系及返回；当前分类和直接邻居保持可见，无关分类的中枢环不再争夺注意力。重置应恢复全局主次。

### 共同比较条件

固定种子、根旋转、动画时间、相机状态、页面内容区尺寸、DPR 和曝光。对比使用至少 1440×900、1280×800 及一组窄屏视口，桌面检查 DPR 1 和 2；不通过放大新版本来制造细节增多的印象。

沿用已有静态、模型与真实 WebGL 交互检查，针对新增输出链、静态端部 alpha 和焦点恢复补充必要验证。检查减少动态、页面隐藏及卸载；新增纹理不得依赖每帧随机变化，减少动态时也要保持稳定。

同设备、同 DPR 下记录修改前后至少 10 秒的帧耗时和绘制调用，比较新增几何量。优先通过批量属性与 Shader 增加细节，不为每个亮片或断点创建单独对象。若成本明显上升，先减少新增装饰和次要柔光，不删除记忆节点或 semantic 关系。

人工查看是独立的验收项。模型断言、构建通过、WebGL 无错误、像素有变化，都不能单独证明已达到参考的光感和复杂度。

## 11. 完成后应留下的结果

保留原始基线、统一输出对照、最终全局/聚焦截图和连续动画，并简要记录最后采用的颜色、曝光、Bloom、主轨宽度和细节数量。说明哪些画面差异由输出校正带来，哪些由美术调整带来，避免后续再次混在一起调参。

本轮文档只提出优化方案。实施、提交、合并和推送不属于本次交付。
