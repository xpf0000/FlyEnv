## 一、总体评价

我认可这次架构方向的调整，而且认为它比前面几轮方案更适合 FlyEnv 当前的开发阶段。但我不建议直接按现有 V1 文档完整实施，应该再调整一次优先级。

这里有一个很有意思的现象：

你最初的目标是简化记忆系统，但经过几轮设计审查，现在的方案虽然去掉了 PostgreSQL、Qdrant、Redis 等依赖，却实现了相当复杂的文件事务、并发控制、崩溃恢复和进程生命周期管理。

换句话说：

基础设施变简单了，但程序内部的复杂度没有同步下降。

同时，真正决定 AI Memory 是否好用的部分——记忆提取质量、检索效果、跨 Agent 使用体验——反而被简化得比较多。

这是我认为现有方案最大的问题。

## 二、第一优先级：真正的风险是记忆效果，而不是存储性能

P0 · 产品效果

这是我最想强调的问题。

现有 V1 使用：

- title。
- summary。
- topic。
- tags。
- 关键词匹配。
- 中文双字匹配。
- Agent 提供多个查询词。

正文不参与搜索，也不支持向量检索。

文档对这种方法的局限性已有清楚说明，这是好的。

2026-11-02-flyenv-ai-memory-design.md



但从产品角度看，它可能是最容易让用户觉得这个记忆功能不好用的地方。

### 举一个实际场景

Agent A 保存：

```
Title:
Ubuntu 25.04 tray popup not responding

Summary:
After upgrading FlyEnv, the system tray popup
stopped responding. Switching to the classic
popup style was a temporary workaround.

Tags:
ubuntu, tray, linux, classic
```

一周后，Agent B 接到任务：

> 之前那个 Linux 托盘点击没反应的问题，最后是怎么处理的？

如果 Agent B 使用关键词 `Linux 托盘 点击无反应`，检索效果就很依赖匹配策略。

如果换成：

> 上次升级之后菜单打不开的问题是什么原因？

召回率就可能进一步下降。

不是信息没有保存，而是找不到。

对于用户来说，记忆存储成功但无法检索，和没有记忆的体验非常接近。

### 我的建议：V1 至少要做三层检索

1

精确检索

title、topic、tags、路径、版本号、Issue ID 等精确匹配。

2

关键词与全文检索

title、summary、tags 的词项组合和模糊匹配；必要时增加正文搜索作为回退。

3

语义检索

作为可选能力，允许接入用户已有的 Embedding 模型或向量服务。

注意，我不是建议现在就引入 Qdrant。

我建议的是：

V1 先实现可扩展的 Retrieval 接口，至少把记忆召回效果作为上线验收条件，而不是只验证搜索代码能返回结果。

可以先用简单检索做实验。

如果 30～50 条真实测试问题中，有大量用户自然表达无法找到正确记忆，那么就应该在正式发布前补充语义检索，而不是机械地坚持 V1 不需要 Embedding。

这与用户是否已经安装 Qdrant 没有直接关系。我们需要先证明当前检索策略足够有用。

## 三、第二优先级：只依靠 Memory Rules，长期记忆可能无法稳定形成

P0 · 产品效果

目前的方案中，Agent 负责决定何时调用 `store`，Memory Rules 提醒它：

- 开始项目任务时检索。
- 遇到重要信息时保存。
- 做出重要决策时更新。
- 不要保存无价值内容。

这些规则本身没有问题。

2026-11-02-flyenv-ai-memory-design.md



但这里有一个根本性的限制：

Agent 不一定会遵循规则，也不一定每次都能准确判断哪些信息值得保存。

我认为这个问题甚至比存储选择还重要。

### 实际使用中可能出现的问题

假设一个 Codex 会话持续运行三个小时。

期间：

1. 分析项目架构。
2. 修改几个模块。
3. 发现历史 Bug。
4. 修复问题。
5. 调整技术方案。
6. 运行测试。
7. 提交代码。

最后因为会话压缩、进程退出、用户切换任务等原因，Agent 没有调用 `memory_store`。

那么这三个小时的经验可能没有任何内容进入长期记忆。

即使存储系统非常可靠，也无济于事。

### 我建议增加两个机制

机制 A：日常自主记忆

保留当前 Memory Rules：

- 开始任务时检索。
- 重要变化时保存。
- 结束任务时总结。

这属于自动工作模式。

机制 B：明确记忆指令

用户随时可以说：

> 记住这个设计决策。

或者：

> 把这次问题的解决过程保存到项目记忆里。

Agent 必须执行保存，并返回确认的记忆 ID。

这能保证重要信息在用户主动要求时得到明确处理。

我还建议在规则中区分两种保存行为：

| 保存模式      | 行为                 |
| --------- | ------------------ |
| Explicit  | 用户明确要求记住，优先执行并反馈结果 |
| Automatic | Agent 自行判断是否具有长期价值 |

后续还可以研究不同 Agent 的 Session Hook 或任务结束 Hook，用于触发记忆整理，但不应该假设所有 Agent 都提供相同的 Hook。

短期内不需要开发自动采集完整会话的能力，但必须验证 Codex、Claude Code 在真实长任务中是否会稳定调用记忆工具。

## 四、第三优先级：项目识别机制需要更符合真实 Agent 的使用方式

P1 · 使用体验

目前设计要求每次项目级 MCP 调用都传入 `project_path`，然后通过 realpath 规范化，映射到一个稳定 UUID。

同名不同路径隔离、worktree 独立、不自动匹配父目录，这些处理都比较严谨。

2026-11-02-flyenv-ai-memory-design.md



但是我担心它会遇到一个实际问题。

### 同一个项目，不同 Agent 的工作目录可能不同

例如：

```
/Users/dev/FlyEnv
/Users/dev/FlyEnv/src
/Users/dev/FlyEnv/plugins/ai-memory
```

Codex 可能在项目根目录工作，而 Claude Code 可能从 `plugins/ai-memory` 子目录启动。

如果它们分别传入当前工作目录，就会出现三个不同的项目 ID。

最终用户看到的是：

> 明明已经保存了 FlyEnv 的记忆，为什么换一个 Agent 就找不到了？

文档明确不允许通过目录前缀自动合并，这是有道理的，因为 monorepo 中的子项目可能确实应该独立管理。

但不能自动合并，不代表不能辅助用户识别项目。

### 我建议

保留当前的项目 ID 方案，但增加一个轻量项目解析策略：

- 优先使用已经明确登记的项目根目录。
- 对于尚未登记的子目录，可以检测父级是否存在已登记项目。
- 如果发现匹配，提供候选项目，而不是自动创建新项目。
- 明确登记以后，后续使用稳定的 `project_id`。
- 不要把 Git remote URL 当作唯一身份标识。

这一项不一定要全部进入 V1，但最少要增加测试：

同一个项目从根目录和不同子目录启动 Agent，是否能够稳定访问同一份记忆？

还有一个问题：V1 将项目搬家后的新路径直接视为新项目，项目重绑定放到后续。

2026-11-02-flyenv-ai-memory-v1.md



我认为可以先接受这个限制，但应该在界面中明显提示，而不是让用户以为原来的记忆消失了。

## 五、第四优先级：文件存储的可靠性设计正确，但存在过度工程化

P1 · 工程复杂度

这一部分我看得比较仔细。

目前设计包括：

- 独占 worker。
- 进程级文件锁。
- 每个 scope 独立写入队列。
- revision 乐观并发控制。
- request_id 幂等处理。
- MD 先写入、JSON 最后提交。
- 原子文件替换。
- 文件同步。
- 历史版本。
- tombstone。
- 删除补偿。
- pending 删除恢复。
- 结果未知状态恢复。
- 固定版本游标。

从可靠性角度看，这些机制大多有合理的理由。

2026-11-02-flyenv-ai-memory-design.md



但是它们加在一起，实际上已经构成了一个小型事务存储系统。

### 我认为这里出现了一个矛盾

原本选择 JSON + Markdown，是因为希望：

> 不需要数据库、不需要复杂依赖，代码简单、可维护。

但为了让多个 Agent 安全地修改这些文件，现在需要自己实现数据库已经非常成熟的部分能力。

| 能力          | 当前文件方案               | 使用事务数据库  |
| ----------- | -------------------- | -------- |
| 多个 Agent 写入 | 自己实现队列和锁             | 数据库事务    |
| 并发修改冲突      | revision 校验          | 乐观锁 / 事务 |
| 原子提交        | 临时文件 + rename + sync | 事务提交     |
| 崩溃恢复        | 自行设计恢复协议             | 数据库恢复机制  |
| 版本历史        | JSON 快照              | 历史表      |
| 索引          | 内存 Map               | 数据库索引    |
| 删除恢复        | tombstone + 清理状态     | 事务及后续清理  |

这并不意味着必须改回数据库。

我更希望指出：

JSON + Markdown 是为了获得开放、易读、容易迁移的数据格式，不应该为了完全不用数据库而无限增加复杂度。

如果文件存储实现到一定阶段，发现大部分代码都在处理事务和恢复，而不是记忆业务，就应该重新评估选型。

不过，目前这套文件方案仍然值得先实现一个原型。

### 我认为有两个机制不能删

1\. 一个写入所有者。

这是多 Agent 并发访问的基础。

特别是 FlyEnv 现有的 worker 池可能同时产生多个执行环境，不能简单依靠某个 JS 单例保证全局一致。

2\. 原子提交 + revision + request_id。

这三者解决真实的数据可靠性问题。

我建议不要为了省代码删掉它们。

### 但有两个地方可以简化

A. 取消 V1 的复杂正文游标分页。

目前文档设计了绑定 revision、bodyId、UTF-8 字节偏移的分页协议。

这个方案技术上合理，但第一版记忆正文最大只有 64 KiB。

如果每条记忆本来就是一个相对独立的主题，我觉得可以在 V1 中限制正文大小，让 `get` 一次返回完整正文。

例如初期限制单条正文在 8～16 KiB 左右，较长资料要求 Agent 分成多条记忆。

这样可以省去一整套正文分页、游标校验、跨版本续读的实现及测试。

以后需要保存长文档时，再引入分页读取。

B. 不必在 V1 实现特别精细的缓存限制。

目前设计最多缓存 8 个 scope，单 scope 最多 1 万条记录，还要处理缓存淘汰、稳定协调对象及旧搜索游标失效。

它比较周全，但这些边界还没有来自真实性能测试的数据支持。

更值得注意的是：目前单条 JSON 上限 2 MiB，同时允许单 scope 1 万条记录，意味着最坏情况下单个项目可能需要处理接近 20 GiB 的 JSON 数据。

虽然最终只在内存中保留元数据，但读取和解析整个 JSON 时仍然需要处理 history。

因此，限制记录条数并不等于控制住了实际内存和 I/O 消耗。

我建议先把单记录 JSON 的大小限制设得更合理，并记录真实加载耗时、记录数和内存使用，再决定缓存策略。

## 六、两个需要修正的可靠性细节

这里是更偏代码实现的审查意见。

### 1. 删除与并发读取之间的语义，需要明确

当前设计要求：

> 删除提交之后，正在读取 MD 的 get 需要再次确认记忆未被删除，避免返回已删除内容。

这个思路没问题，但存在一个微妙的竞态。

例如：

```
T1：Agent A 开始 get
T2：Agent A 读取 MD
T3：Agent A 检查记录尚未删除
T4：Agent B 提交 forget
T5：Agent A 的响应才发送到客户端
```

如果仅仅在返回之前检查一次 tombstone，并不能保证删除之后绝对不会出现一个之前已经开始的读取结果。

我的建议是明确两种操作的线性化顺序：

- 如果 get 已经在 forget 之前完成逻辑读取，可以允许它返回当时的有效快照。
- 如果 forget 已经完成，后续新发起的 get 必须返回 deleted。
- 如果要求更加严格的并发读取顺序，就需要额外的读写协调，而不仅是返回前复核文件。

这里不建议追求无法实现的承诺：已经进入某个 Agent 上下文的记忆，不可能通过 MCP 服务端删除来撤回。

此外，删除文件不等于 SSD 上的物理安全擦除。V1 可以承诺清除受管理文件及索引，但不要将其描述为取证意义上的彻底清除。

### 2. `projects.json` 可能成为一个集中故障点

目前每条记忆都有独立 JSON，单条损坏可以隔离，这是个好设计。

但所有项目映射集中在 `projects.json` 中，一旦损坏，可能导致整个项目映射无法使用。

文档已经选择阻断请求，而不是自动初始化空文件覆盖，这个处理是正确的。

我建议补充：

- `projects.json` 同样采用可靠的原子提交。
- 项目注册成功后有明确的持久化确认。
- 建立可以恢复的项目映射备份或快照。
- 恢复过程中不能自动猜测项目身份后直接覆盖原映射。

尤其是你之前已经遇到过数据丢失问题，我认为数据备份的重要性应该高于复杂的历史浏览界面。

## 七、FlyEnv 集成方案，我基本认可

这一块是三份文档中我比较认可的部分。

文档识别了几个实际宿主接入问题：

1. 插件 Manifest 目前缺少通用 MCP 工具声明。
2. 原有 worker 池不一定保证记忆数据的唯一写入者。
3. 插件更新和卸载需要等待真实 worker 退出。
4. MCP 与 UI 必须访问同一份状态。
5. 新老插件版本需要进行兼容性校验。

对应的方案是：保留 FlyEnv 原有 MCP 网关，新增声明式插件 MCP 工具注册和专属 worker 路由。&#x20;

2026-11-02-flyenv-ai-memory-design.md



我认为这是合理的。

它不仅能够服务于 AI Memory，未来其他 FlyEnv 插件也可能需要向 Agent 动态暴露自己的 MCP 工具。

相比每个插件单独启动一个 HTTP MCP Server，这种方式更符合 FlyEnv 现有产品结构。

不过需要注意：这些宿主问题是设计文档对现有代码的分析。我没有在本轮完整审计当前仓库所有相关代码，因此不把每个细节都视为已经复现的问题。

### 我更推荐的实现顺序

先完成一个通用能力：

```
Plugin Manifest
       |
       v
MCP Tool Registration
       |
       v
Tool Dispatcher
       |
       v
Dedicated Worker
       |
       v
Plugin Business Logic
```

用一个极简示例工具完成以下验证：

- 安装插件后，MCP 工具出现。
- 禁用插件后，工具不可调用。
- 插件升级后，不存在新旧 worker 同时写入。
- UI 和 MCP 能访问相同的 worker 状态。

通过这些验证后再实现记忆业务。

不要一边开发 Memory Engine，一边改整个插件和 MCP 基础架构，否则出了问题很难区分到底是哪一层导致的。

## 八、产品体验上，我认为 V1 还缺少一个关键能力

P1 · 产品体验

就是 真正的一键接入。

你最初的设想是：

> 用户在 FlyEnv 安装插件后，就可以很方便地让现有 AI Agent 具备长期记忆能力。

但 V1 最终设计的是：

- FlyEnv 自动配置 MCP。
- Memory Rules 需要手动复制。
- 用户自己找到 Agent 的配置位置。
- 用户手动安装规则。
- 然后再测试是否生效。

文档明确将规则自动安装放到后续。

2026-11-02-flyenv-ai-memory-v1.md



从开发风险看，这个取舍合理。

但是从产品体验看，它削弱了 FlyEnv 原本最有优势的地方。

我认为至少对于两个优先支持的 Agent：

- Codex
- Claude Code

应该研究是否能提供完整的一键接入。

用户选择 Agent 后：

```
Configure Memory
       |
       +---- Configure MCP
       |
       +---- Install Memory Rules
       |
       +---- Verify Connection
       |
       +---- Ready
```

当然，规则自动安装必须避免覆盖现有配置，可以使用独立文件、受控配置块或可恢复的合并方式。

如果这个功能暂时来不及实现，我建议将手动安装版本定义为开发者预览版，不要把它当作最终完成的一键接入体验。

## 九、我还建议增加一个功能：Memory Diagnostics

这一点前面几轮方案都没有给予足够重视。

对于记忆系统来说，用户遇到问题往往很难知道原因。

例如：

> 为什么 Claude Code 没记住我之前说的事情？

可能有四种原因：

1. Agent 根本没有调用保存工具。
2. 保存工具调用了，但写入失败。
3. 记忆保存成功，但 Agent 没有调用搜索。
4. Agent 搜索了，但没有检索到正确内容。

这四种情况的修复方式完全不同。

所以我建议 V1 增加最基本的诊断信息。

| 记录                  | 用途             |
| ------------------- | -------------- |
| MCP Tool Invocation | Agent 是否调用了工具  |
| Store Result        | 记忆是否保存成功       |
| Search Query        | Agent 实际搜索了什么  |
| Search Result Count | 是否找到结果         |
| Tool Error          | 是否发生连接、权限或写入错误 |
| Client / Agent      | 哪个 Agent 调用了工具 |

这个功能不需要独立的日志服务器。

可以使用 FlyEnv 现有的日志能力，或者为插件维护一个小型滚动诊断日志。

默认避免记录敏感正文，必要时允许用户显式开启更详细的诊断。

我甚至认为：

Memory Diagnostics 对第一版的价值，可能比 Memory Dashboard 更大。

因为你准备自己长期使用并逐步优化，有了这些数据，就能判断记忆失败究竟发生在哪个环节。

# 十、重新整理 V1：我建议如何调整？

我不会推翻目前的 V1。

它的大部分核心设计已经比较成熟，需要调整的主要是开发优先级。

| ------------------ | ----- | -------------------------- |
| JSON + Markdown    | V1    | 保留                         |
| 项目隔离               | V1    | 保留，增加目录差异测试                |
| 专属 Worker          | V1    | 保留                         |
| 原子提交和版本控制          | V1    | 保留                         |
| 幂等与崩溃恢复            | V1    | 保留                         |

| 正文固定版本分页           | V1    | 建议后置                       |
| 固定 8 Scope 缓存      | V1    | 简化，按测试优化                   |

## 我推荐的开发顺序

1. 第 1 阶段：先证明这个记忆系统有用

   独立实现最小 Memory Engine，包括主题化 JSON/MD、基础搜索、MCP 工具、Memory Rules。

   先不接 FlyEnv 的完整 UI，也不急于实现所有复杂的缓存和游标协议。测试时使用单一写入进程，避免把尚不安全的原型暴露给多个 Agent 同时写入。
2. 第 2 阶段：解决可靠性和并发

   统一 worker、排他锁、原子写入、revision、request_id、删除恢复、故障注入。

   只有这部分通过验证，才允许多个 Agent 同时正式使用。
3. 第 3 阶段：接入 FlyEnv 插件体系

   通用 MCP 工具注册、专属 worker 路由、生命周期管理、基础记忆页面。

   优先完成 Codex 和 Claude Code 的实际接入。
4. 第 4 阶段：真实使用和效果优化

   用日常项目连续使用，收集诊断数据，测试检索召回、重要记忆保存率和跨 Agent 共享效果。

   根据结果决定是否引入 Embedding、全文搜索或更高级的记忆处理。

# 十一、我建议增加一组真正面向产品效果的验收标准

现有 V1 的验收测试非常重视工程可靠性，包括：

- 同一请求重试。
- 并发写入。
- 插件升级。
- worker 崩溃。
- 文件损坏。
- 删除失败。
- 游标有效性。

这些都应该保留。

但当前只有约 10 条真实问题用于检索和 Agent 使用验证。

2026-11-02-flyenv-ai-memory-v1.md



我认为这不够验证一个记忆产品。

建议建立一个小型但真实的测试集。

### 推荐的测试维度

| 维度      | 测试内容               | 我建议的初始目标        |
| ------- | ------------------ | --------------- |
| 保存能力    | 用户明确要求记住           | 100% 有明确保存结果    |
| 记忆召回    | 自然语言搜索历史信息         | Recall\@5 ≥ 85% |
| 记忆准确性   | 返回的记忆是否对应真实来源      | 不允许编造来源         |
| 更新能力    | 用户修改已有决策           | 不再将旧版当作当前版本     |
| 项目隔离    | 不同项目间检索            | 无错误跨项目结果        |
| 跨 Agent | Codex 保存、Claude 读取 | 核心流程全部通过        |
| 自动记忆    | 重要事件是否主动保存         | 记录覆盖率，持续调优      |
| 故障恢复    | 崩溃后可恢复已确认操作        | 不出现静默丢失         |

这里的 85% 是建议的产品目标，不是已有结果。如果实际基准数据比较难，需要根据测试集定义再调整。

我还建议增加一个对照组：

直接使用原始 `memory` Skill 和 `MEMORY.md`，与 FlyEnv Memory Plugin 比较。

因为你最初就是从这个简单 Skill 得到了启发。

那么新插件应该明确证明自己比原始 Skill 多解决了什么问题。

例如：

- 是否更容易找到历史记忆？
- 是否减少重复上下文？
- 是否能够正确更新旧记忆？
- 是否能跨 Agent 使用？
- 多 Agent 同时工作时是否更可靠？

如果最终效果没有显著区别，仅仅是代码和架构更复杂，就说明还没有抓住真正的产品价值。

# 十二、最终结论

我认为这次方案已经找到了比较合适的方向。

JSON + Markdown、主题化记忆、Agent 负责理解、插件负责存储和检索、FlyEnv 统一提供 MCP 接入，这几个核心决策我都支持。

但是我建议把注意力重新分配一下。

## 我最建议保留的 3 个设计

JSON 元数据 + Markdown 原文

简单、透明、可以阅读和迁移，非常适合本地长期记忆。

单一 Memory Worker

解决多 Agent 共享同一份记忆时的状态一致性问题。

MCP + Memory Rules

保持模型和 Agent 无关，不要求用户另行配置一个 LLM。

## 我最建议修改的 3 个地方

提高记忆召回的优先级

不要让检索效果成为最薄弱的环节。

简化过早引入的底层机制

特别是正文分页、复杂缓存限制和未经过真实负载验证的优化。

增强实际使用闭环

包括自动记忆的可靠触发、Agent 接入体验和 Memory Diagnostics。

还有一个工程上的判断：

现在 V1 文档虽然很详细，但并不等于项目已经准备好直接进入全面开发。跨平台文件锁、原子文件替换和 worker 生命周期，是应该先用小原型验证的三个技术前置条件。如果其中任何一个在 FlyEnv 当前架构下实现成本明显高于预期，就应该及时调整存储或运行方式，不要被已经写好的设计文档束缚。

我最核心的建议是：V1 应该优先证明「记得住、找得到、用得上」，再用必要的可靠性机制保证「不会丢、不会乱、不会串项目」。

现在这份设计对后面三个问题考虑得非常充分，但对前面三个问题还不够重视。

我认为把这个优先级调整过来之后，这个方案就很值得正式进入原型开发阶段了。
