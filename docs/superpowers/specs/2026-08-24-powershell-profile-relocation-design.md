# PowerShell Profile Relocation Design

## Goal

Allow the Windows shell integration to update a PowerShell profile when the
user's Documents known folder has been relocated outside the user home
directory.

## Scope

The change applies only to the `installFlyEnvPowerShellIntegration` operation.
It removes the requirement that a requested profile target be under the helper
user's home directory.

The following safeguards remain unchanged:

- The runtime script must be the approved `bin\\flyenv.ps1` under a configured
  FlyEnv data root.
- A profile target must use a supported edition: `windows-powershell` or
  `pwsh`.
- A target must retain the edition-specific standard profile directory and
  filename:
  `WindowsPowerShell\\Microsoft.PowerShell_profile.ps1` or
  `PowerShell\\Profile.ps1`.
- Paths are normalized and rejected when they contain a reparse-point
  component.
- The operation accepts at most one target per edition and updates only the
  FlyEnv-marked integration block, preserving the rest of the profile.

## Architecture

The renderer/fork layer already derives profile paths from Windows' resolved
Documents folder. It will continue to send those paths unchanged. The helper
operation has three implementations that validate the same request:

1. The Go helper validates paths before writing profiles.
2. The TypeScript UAC fallback validates paths before constructing its command.
3. The fallback's elevated PowerShell payload validates again before writing.

All three validators will remove only their user-home containment check. They
will retain the standard directory/filename, edition, normalization, and
reparse-point checks so the Go helper and fallback keep equivalent behavior.

## Security

The written profile content is generated by FlyEnv rather than passed through
as arbitrary profile content, but it is not entirely static: FlyEnv merges its
marked block into the existing profile and references the validated runtime
script path. The retained restrictions constrain the privileged operation to
the two known PowerShell profile targets and to FlyEnv's approved runtime
script. Removing the home containment check is required because Windows can
relocate Documents to a different local volume or network-backed folder.

## Testing

Add regression coverage for a redirected Documents path outside the helper
user home. The Go helper utility test and TypeScript shell-integration test
must demonstrate that the target is accepted while malformed profile names,
unsupported editions, duplicate editions, reparse points, and unapproved
runtime-script paths remain rejected by their existing checks.

## Non-goals

- Changing how Windows resolves the Documents known folder.
- Generalizing this privileged operation into arbitrary file writing.
- Changing runtime script validation, content reconciliation, or profile
  encoding behavior.
