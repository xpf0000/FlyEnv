# Dameng DM8 Plugin Implementation Plan

> **For agentic workers:** Use the project module/failure boundaries and parallel-agents skill for independent renderer and media research work; integrate and review before delivery.

**Goal:** Deliver a standalone DM8 plugin with official downloads, owned installation discovery, explicit initialization, normal service lifecycle, configuration, logs, license information and official uninstallation.

**Architecture:** Plugin-local renderer singleton owns asynchronous operations and persisted nonsecret settings. Fork owns package verification, cross-worker locks, manifests and processes. Linux reuses `serviceStartSpawn` and Base SIGINT stopping; Windows adapts the existing lifecycle to official service control.

**Tech Stack:** TypeScript, Vue 3, existing FlyEnv plugin builder and runtime, Node native filesystem/process APIs.

**Spec:** `docs/deepwiki/dameng.md` (user reviewed and requested implementation).

## Global Constraints

- No new Pinia store, host module enum entries, Helper changes, cross-plugin private imports or bundled database media. Shared configuration use is limited to the user-authorized existing custom-version dirs integration described below.
- Official HTTPS sources only; exact Windows x64/Ubuntu 22 x86_64 gate, including native architecture detection on Windows.
- Install into final immutable program path; staging only for media. Keep data after uninstall.
- Persist nonsecret settings with StorageGetAsync/StorageSetAsync; passwords remain in session request snapshots, never settings/manifests; internal IPC follows the existing ordinary transport.
- No license acceptance page or confirmation IPC.
- Current development host cannot validate x64 database lifecycles. Package remains experimental; no claims of real-platform acceptance or automatic publication.
- Work stays in current checkout; new plugin files are isolated by directory. No commits, VM changes or installation into the host are part of this task.

## Review Focus

- Cross-worker installation/lifecycle races: filesystem admission locks; unknown outcomes prevent blind replay.
- Tampered renderer paths/manifests: derive package identity from the pinned catalog, validate user-selected program destinations, and reuse only the canonical path in the owned installation record; validate executables and instance configuration.
- Installer completed before registration failure: preserve installed facts, never recursively erase program/data or replay installation.
- Worker recycling and shutdown: Linux stopping uses persisted owned PID and exact instance markers, Windows uses service plus PID ownership.
- Credentials changed/invalid and timeout: report authentication separately, hide secrets, stop only the process created by this request.

## Operation Contracts

- Catalog/instance information: renderer singleton owns request and listener through terminal; duplicate reads share in-flight Promise; code 200 progress is nonterminal; code 0 success/other failure release listener; page unmount does not cancel operation.
- Install: singleton owns snapshot, progress and duplicate Promise; Fork owns global install lock and official installer. Verification/install/manifest are required; media release and refresh notices supplementary. Installed-but-incomplete remains partial/unknown, cannot replay.
- Initialize: singleton owns snapshot and progress; Fork holds same-install lifecycle lock, validates empty owned instance directory and immutable parameters, runs dminit once, publishes manifest only after verifying dm.ini. Failure preserves files; no overwrite retry.
- Start/stop/restart: ModuleInstalledItem owns renderer lifecycle; startExtParam supplies session credentials and nonsecret settings, stopExtParam no secrets. Fork holds per-install lock and owns PID/exit confirmation; default SIGINT Linux; Windows SCM stop. No force kill/stop of external instance, no cleanup success before exit.
- Uninstall: singleton owns operation; Fork locks install globally and lifecycle locally, requires normal stop then official uninstaller. Data retained. Failure keeps manifest and partial outcome; no sibling operation replay.
- Lifecycle verification covers duplicates, progress then terminal cleanup, page reentry, failure retry, process ownership, worker restart, and shutdown. Changes to entry/controller are checked by renderer-operation-boundaries.
