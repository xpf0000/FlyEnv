# MySQL Cluster startup corrections

User requests credential-free ordinary process startup, unique create/edit names, and multiple cluster targets in a startup group. Existing plugin-only constraint remains; any unavoidable host change requires a narrowly scoped exception. No new shared configuration or Pinia state.

## Contracts and failure boundaries

- Existing singleton controller owns lifecycle admission, immutable requests, progress, duplicate/conflicting calls, terminal notices, and cleanup across view changes. Actual members continue through ModuleInstalledItem.start/stop/restart. Ordinary lifecycle success means the owned process started/stopped; no SQL login, replication setup, or credential dialog decides this result. First creation still sets the supplied root password and explicitly configures replication as required dependencies. Fork owns child/PID identity and uses the shared process startup helper; initialization root password remains required only before its initial application.
- Replication status is an explicit refresh observation, independent from process lifecycle. Lifecycle refreshes must not authenticate or wait for SQL status. Explicit replication configuration/recovery has its own group operation, all-running precondition, credential snapshot, progress, re-entry guard, and terminal result. Failed SQL configuration cannot undo completed process starts. Existing safe GR recovery must remain reachable without putting it back in ordinary start.
- Process refresh and explicit SQL observations use separate singleton-owned flights. A pending manual SQL observation cannot delay stop/start; observations use credential/PID snapshots and cannot overwrite a newer stopped/restarted process. Unknown/failed observations are local results. Ordinary replica restart resumes the saved channel via version-compatible arguments, and ready replica/GR nodes start read-only. Explicit replication account provisioning temporarily relaxes only super_read_only for required administrator DDL, then restores its original protection even on failure; failed restoration propagates as a required failure.
- Name validation is a required create/edit precondition in both form and serialized catalog mutation. Group names are unique among groups; member names among instances; comparisons trim and fold case, edits exclude their own IDs. Legacy catalogs remain readable. Rejected duplicates cause no filesystem or catalog mutation; concurrent creates serialize at the existing catalog boundary.
- Multi-selection policy belongs to the native StartupGroup candidate builder, which currently hardcodes PHP-FPM. A concrete three-file generic patch was prepared for review without modifying the repository. User explicitly chose **keep host unchanged, defer multi-selection**; patch not applied and temporary draft removed. This item is intentionally deferred, not claimed as delivered.
